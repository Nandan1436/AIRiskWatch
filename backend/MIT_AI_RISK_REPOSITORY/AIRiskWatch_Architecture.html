Live ingestion AIRiskWatch System Architecture v1.2 — MIT only

AI Incident Intelligence Platform

AIRiskWatch

From scattered news reports to a queryable risk knowledge base.

Every incident is scraped, screened for relevance, and zero-shot classified by an LLM against the MIT AI Risk Taxonomy — risk domain, subdomain, entity type, timing, and intent. De-duplication uses a sentence transformer for candidate retrieval followed by an LLM tie-breaker. CSET and GMF annotations from the seed corpus are imported as-is for existing incidents; live classification of new articles uses MIT only in v1. Two independent read paths serve the results: global SQL trend analytics on the home page and a semantic RAG search page — neither depends on the other.

Why this project

// the problem, in plain terms

Safety frameworks tell organisations which controls they should have.
Incident databases show what actually went wrong.
Almost nobody connects the two. AIRiskWatch is that bridge.

The pain

AI harms are scattered

Real-world AI failures are buried across hundreds of news sites in plain prose. There is no single, structured, searchable place to ask "what has actually gone wrong, and to whom?"

The pain

Frameworks float free of evidence

NIST, the EU AI Act and UK Gov publish long menus of controls, but with no empirical grounding for which ones matter for which real harms. Analysts bridge that gap by hand in spreadsheets.

The answer

One living knowledge base

Continuously scrape incidents, classify them with an LLM against multiple taxonomies, and serve trends + plain-language search to policymakers, developers and researchers.

The answer

Evidence-backed governance

Link each real harm to the framework controls that address it — so a policymaker can say "this risk is growing, here are the controls and here is the evidence," in minutes instead of days.

What makes it different

// the features I am explicitly building
01

MIT taxonomy — the classification backbone

Every new article is zero-shot classified by an LLM against the MIT AI Risk Taxonomy across five axes: risk domain, subdomain, entity type, timing, and intent. Low seed counts and class imbalance rule out trained classifiers — zero-shot generalises to new subdomains without retraining. CSET and GMF annotations are imported from the seed corpus for existing incidents, not live-classified in v1.

02

Evaluation pipeline — empirical validation

The 1,242 human-annotated MIT labels in the seed corpus serve as a held-out evaluation set (150–200 incidents held back). We run the LLM classifier and measure precision/recall per domain against the human annotations — directly justifying the zero-shot decision and providing academic rigour that trained-classifier baselines cannot match on this dataset size.

03

Automatic de-duplication

Ten sites reporting one event collapse into one incident with many reports — via a fine-tuned multi-qa-MiniLM-L6-cos-v1 sentence transformer (top-5 candidate retrieval) then an LLM tie-breaker. A 2025 study on this exact AIID task reports 98.7% Accuracy@5, validating the approach.

04

Plain-language semantic search (RAG)

"What incidents has an AI navigation aid for blind users caused?" → embed query → ANN retrieval → cited, synthesised answer plus matched incident cards. This is a separate read path from the home-page trend charts — search never produces analytics; analytics never depend on a user query.

05

Harmed-party filtering from seed data

The seed corpus already contains semi-structured harmed-party slug arrays (e.g. ["pedestrians","women","minors"]) for all 1,498 incidents — imported as a text[] column and queryable with WHERE 'pedestrians' = ANY(harmed_parties) at zero extra LLM cost. Full canonical-vocab normalisation for live-scraped articles is a v2 extension.

06

Fully automated & self-growing

A daily cron grows the base with no human in the loop — every step is an LLM or deterministic call. Uncertain items are auto-flagged with a confidence score, not gated by a person.

Open questions & design decisions

// the ones I expect to be asked
?

Do I actually need a knowledge graph?

Decision · not yet
No — PostgreSQL + pgvector covers every current use case. The entity links (developer → deployer → harmed party) live fine in relational tables, and semantic search is served by vector similarity + RAG, not graph traversal. A knowledge graph (and Graph-RAG on top of it) only earns its place once queries become genuinely multi-hop — e.g. "find harms caused by systems built on the same foundation model as X." That is a clean future extension, not a v1 requirement. Building it now would add infrastructure and effort for value we cannot yet demonstrate.
?

Same event on 10 sites — how do I avoid duplicate incidents?

Rule
Each report is embedded and matched (vector + shared entities) against existing incidents; an LLM makes the final "same incident?" call. If yes → it is attached as another report under the existing incident; if no → a new incident row is created. This is the AIID model: one incident, many reports. Published research on exactly this AIID task reports ~98% top-5 match accuracy with title+description embeddings, which de-risks the approach.
?

Same harm, but a different AI system / different org — one incident or two?

Rule
Two separate incidents. An "incident" is a specific real-world event — defined by who/what/when/where, not by the type of harm. Different AI system or different deploying organisation ⇒ different event ⇒ different incident, even if the harm looks similar. They are not lost, though: they link upward to the same risk class in the taxonomy, so trend analytics still group them. Matching keys for dedup: AI system + deployer + victims + time window + event description — not the harm label alone.
?

Should cyclist / motorcyclist / driver be one harmed party, or many?

Decision · not in v1
No — the seed corpus already provides clean slug arrays. The incidents.csv file contains structured harmed-party slugs (["pedestrians","women","minors"]) for all 1,498 incidents — already semi-normalised, not free text. These are stored as a text[] column and filtered with WHERE 'pedestrians' = ANY(harmed_parties) at zero extra LLM cost. For newly scraped articles, the LLM extracts harmed parties as raw text; full canonical-vocab normalisation (cyclist → road user hierarchy) is deferred to v2 — it only matters once live-article charts need the harmed-party dimension.
?

Is the mitigation / framework data actually useful?

Decision · not in v1 — future extension
The 831-control mitigation framework is a genuine differentiator but not a v1 requirement. The core value proposition — linking real incident data to governance frameworks — still holds; it just isn't implemented in the first build. In v1 the analytics page shows MIT domain trends, incident counts over time, and filters by domain/date, which is already a complete and demonstrable product. The framework-crosswalk layer (mapping MIT subdomains → NIST / EU AI Act / UK Gov controls) is a clean v2 addition: it requires one LLM mapping pass at the taxonomy level and a few extra DB columns, not a pipeline redesign.
?

LLM or trained classifiers for taxonomy tagging?

Decision · LLM zero-shot (MIT only in v1)
The data volume rules out trained classifiers for any of the three taxonomies. MIT has ~30 subdomains across 1,498 incidents — roughly 50 examples per class before accounting for severe imbalance (Domain 7 alone covers ~40% of incidents). CSET covers only 214 incidents (14%), GMF only 326 (22%) — neither has enough labelled examples for reliable supervised models. LLM zero-shot with MIT taxonomy definitions handles classification in a single structured-output call, generalises to new subdomains without retraining, and produces results comparable to trained classifiers on sparse data. CSET and GMF are imported from the seed CSVs for existing incidents; live-article classification for those two is deferred. The 1,242 MIT-annotated seed incidents serve as the evaluation set — hold out 150–200, compare LLM output vs. human labels, report precision/recall per domain.
?

The CSET table has 66 columns — how many does the LLM actually classify on new articles?

Decision · 0 LLM-classified CSET fields in v1
Two things must not be conflated: columns stored in the DB (imported once from the seed CSV — no LLM involved) vs. fields the LLM produces for new scraped articles. In v1, the LLM classifies only MIT taxonomy fields for new articles — domain, subdomain, entity type, timing, and intent. No CSET fields are live-classified: only 214 of 1,498 seed incidents have CSET annotations, which is too sparse to make CSET charts meaningful for new data anyway. The full CSET columns already in the seed import live in the DB and are available for seed-corpus analytics — they just aren't extended to newly scraped articles yet. Adding live CSET classification later is a two-step operation: add the columns to the LLM prompt, then run a batch retroactive pass on the existing scraped articles.
?

Does semantic search produce the trend charts?

Decision · no — two completely separate read paths
No. Home-page trends and the search page share the same database but nothing else. Home page: SQL GROUP BY aggregations on structured columns (mit_domain, sector, harm_level, date) across the whole incident table — no embeddings, no user query involved. Search page: user query → embed → pgvector ANN (top-5) → LLM synthesises a cited answer → returns answer text + matched incident cards. No SQL aggregations, no charts. The structured columns (MIT domain, CSET fields) feed the charts; the embeddings feed the search. Neither path knows the other exists.
